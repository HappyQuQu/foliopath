# FolioPath 交付与架构治理

## 状态与目的

本文规定 FolioPath 如何把已确认产品范围转换为架构输入、实施切片和版本门禁。它是当前交付
治理规范；`api/openapi.yaml` 已成为 HTTP 结构权威，TypeScript 生成类型、唯一 Web API
client、摘要锁、语义兼容检查和 CI 工作流已建立；首次原生 amd64/arm64 PR CI 已通过。
容器和发布流程仍未实现，不能由本规范的目标描述推断为已完成。

本文补充而不替代：

- [产品需求](../product-requirements.md)与[需求确认记录](../requirements-checklist.md)；
- [架构](../architecture.md)与[已接受 ADR](../adr/)；
- [开发就绪评审](../development-readiness.md)、[路线图](../roadmap.md)和[测试策略](../testing-strategy.md)；
- 仓库根目录的 [`AGENTS.md`](../../AGENTS.md)。

发生冲突时不得以代码现状或个人偏好静默裁决，应按下述权威层级暂停受影响工作并完成决策。

## 决策权威

| 层级 | 权威来源 | 决定什么 | 改变方式 |
| --- | --- | --- | --- |
| 产品基线 | 已确认 PRD、RQ 与明确非目标 | 用户价值、用户可见行为、MVP 归属和验收结果 | 新增变更记录并取得产品确认；不得覆盖历史确认记录 |
| 架构基线 | 已接受 ADR、架构和安全/数据模型 | 运行拓扑、信任边界、持久化语义、依赖方向和关键技术选择 | 新增替代 ADR；在 ADR 被接受前不得实现新方向 |
| 可执行契约 | `api/openapi.yaml`、只追加 migration、生成配置 | HTTP 结构、数据库演进和生成边界 | 修改源契约、评审、迁移并通过漂移检查；生成文件不得手改 |
| 交付基线 | 路线图、开发就绪、测试策略、风险登记和 Gate 记录 | 顺序、入口/出口、证据和发布判断 | 记录 Gate 决策并同步受影响文档 |
| 实施约束 | `AGENTS.md` 与项目结构规则 | 代码放置、不可破坏的不变量和验证要求 | 架构变化先有 ADR；产品变化先有产品确认 |

补充规则：

1. 提案、spike 和实现代码都不能覆盖已确认产品基线或已接受 ADR。
2. 产品决策回答“做什么和属于哪个版本”，ADR 回答“系统为何采用这种结构”；二者冲突时必须同时修复，不能假设其中一份自动失效。
3. 已接受 ADR 和已发布 migration 采用追加式历史。方向变化使用“被替代”关系，不回写成仿佛旧决定从未存在。
4. 当前 `api/openapi.yaml` 已是 HTTP 结构化权威，[API 设计](../api-design.md)只解释动机与
   实现参数；任何公开 API 行为变化必须先修改并评审权威契约。
5. 文档状态必须区分“已确认”“已接受”“提案”“已验证”和“已发布”，不得用其中一个替代另一个。

## 产品范围如何进入架构

每个进入实施的 FR/NFR 都必须在[需求—架构追踪表](traceability.md)中回答以下问题：

- 由哪个 capability 拥有业务规则，哪些 adapter 实现外部访问；
- 影响哪些 API、用户流程、数据表、migration 或派生文件；
- 改变哪些信任边界、权限、资源预算、失败恢复或运维流程；
- 受哪些 ADR、风险和非目标约束；
- 用什么 unit、integration、HTTP/E2E、容器、恢复或 benchmark 证据验收；
- 属于哪个 roadmap 阶段和目标版本。

任何字段不适用时写明 `N/A` 及理由，不能留空。若映射暴露了新的部署单元、持久化系统、信任边界或不可逆迁移，应升级为架构变更并先写 ADR。

质量属性不能只写成形容词。安全、可靠性、性能和运维要求至少使用以下场景格式：

```text
刺激：发生了什么
环境：在何种负载、故障或部署条件下
系统响应：必须保持或拒绝什么
可测结果：用什么 fixture、指标或状态判断
```

## MVP Scope Lock

当前冻结产品基线命名为 `MVP-2026-07-23`，其不可变 revision、精确 FR/NFR、验收 ID、
非目标和确认事件由 [scope manifest revision 1](../releases/MVP-2026-07-23-scope.md)固定。
PRD 和路线图负责解释需求与交付顺序，不能通过直接编辑它们改变冻结 manifest。

范围冻结只表示“做什么”已经确认，不表示架构可行性、实现、测试或发布已经完成。

范围控制规则：

1. 新的用户可见能力、格式、配置或角色默认进入 MVP 之后，不自动加入当前冻结版本。
2. 修复实现使其符合既有 FR/NFR，不算扩展范围；改变既有验收行为属于范围变更。
3. 新能力要进入冻结 MVP，必须提供变更记录、目标用户问题、验收标准、完整影响分析和明确产品确认。
4. 进入冻结 MVP 的新增能力必须同时延期一个同等或更高成本/风险的现有项，或记录一次性
   scope-budget exception。exception 必须有唯一 ID、定量/定性预算、产品与架构批准角色、适用
   revision、失效日期/条件和被重新打开时必须重跑的 Gate；它不能自动沿用到下一 revision 或版本。
5. 变更若触及架构、安全、数据模型、API 或部署，应在实现前完成相应 ADR/契约/文档更新并重跑受影响 Gate。
6. 原媒体只读、路径隔离、失败扫描不清理旧索引、无认证不公开暴露等产品与安全不变量不得作为范围交换项或豁免项。
7. 已合入的 scope manifest 不原地改写；获批变化产生新的 revision 文件或后续版本 manifest，并
   在新旧记录中建立替代关系。
8. 不为 MVP 之后的功能预建服务、表、字段、通用框架或抽象层；真实需求进入目标版本后再设计。

## 变更分级

| 等级 | 定义 | 最低记录与审批 | 是否可直接开发 |
| --- | --- | --- | --- |
| C0 文档澄清 | 不改变行为、契约、风险或版本范围 | 文档评审；修复所有交叉引用 | 可以 |
| C1 基线内实施 | 已有 FR/NFR，架构和契约边界不变 | 需求链接、追踪映射、实施项 DoR | 通过切片入口后可以 |
| C2 产品/契约变更 | 改变用户行为、格式、配置、API 语义或目标版本 | Change Record、产品确认、影响分析；需要时更新 OpenAPI/PRD | 完成确认和受影响 Gate 后 |
| C3 架构变更 | 改变部署拓扑、信任边界、持久化、依赖方向、核心技术或运行约束 | C2 所需内容（若用户可见）+ 新 ADR + 架构负责人批准 | ADR 被接受且 Architecture Ready 后 |
| C4 紧急安全/完整性修复 | 延迟处理会扩大安全、数据或供应链损害 | 最小安全评审与测试；同一变更或发布前补齐 Change Record/ADR | 仅限修复必要范围，不得夹带功能 |

仅重构不自动等于 C0/C1。若重构改变包所有权、持久化顺序、并发语义或故障恢复，应按实际影响升级。

C0 和已批准切片内的低风险 C1 修复使用轻量记录：链接现有需求/Gate、说明受影响不变量并提供回归
测试，不需要为每个小修复新建完整 Gate 或 Change Record。新的用户能力、高风险 C1、C2/C3 和 C4
必须使用完整影响与决策记录。

## 阶段与版本

路线图阶段描述交付依赖，不等同于发布版本：

- 阶段 0：冻结产品输入并取得关键可行性证据；
- 阶段 1：建立可运行骨架、契约和工程护栏；
- 阶段 2～4：交付媒体库/扫描、浏览/缩略图、查看器/搜索等纵向能力；
- 阶段 5：加固阶段 1 已建立的认证边界，并完成稳定发布所需的安全、恢复、合规与多架构交付。

版本规则：

1. `MVP-2026-07-23` 只有在阶段 0～5 的出口条件、PRD MVP 验收、测试策略发布门槛和发布阻断风险处置全部完成后，才能作为稳定 MVP 发布。
2. 阶段 1～4 可以产生明确标识的开发预览版，但不能称为稳定 MVP；认证完成前必须遵守回环地址或可信认证代理限制。
3. 进入 Release Candidate 后冻结功能，只允许发布阻断缺陷、安全/数据完整性修复和文档一致性修复。其他变更自动进入下一版本。
4. 每个发布候选必须有版本清单，列出包含的 FR/NFR、ADR、API/schema 版本、目标平台、验证证据、已知限制和残余风险。
5. 阶段完成不能替代版本发布 Gate；版本发布也不能将尚未通过的阶段条件事后改写为已完成。

建议的版本状态为：

```text
Proposed → Scope Frozen → Architecture Ready → In Delivery → RC → Released
                      ↘ Conditional / No-Go
```

## 后端优先、契约驱动的纵向切片

“后端优先”表示先证明安全边界、业务语义、持久化和 HTTP 契约，再让 UI 消费稳定契约；它不表示先建设一个超出当前切片的大后端。每次只设计当前切片所需的端点、表和能力接口。

允许提前的前端工作仅限已通过 S0、进入 S1 的当前切片直接需要的最小应用壳、token 和基础原语，
并须有明确时间盒。可丢弃原型不得进入生产 import graph、不得形成独立契约，评审结束后删除或按
已接受架构重建；不能把任意未来 feature 改名为“共享组件”绕过 Backend Ready。

在首个安全纵向切片通过集成 Gate 前，不并行铺开搜索、查看器、分享、EXIF、watcher 或其他独立能力。后续仍应限制未穿过集成 Gate 的在制切片；被阻塞切片只有在 Gate 记录明确重排后才可让位。

### Gate S0：Architecture Ready（Slice Selected）

必须具备：

- 目标版本、roadmap 阶段和稳定 FR/NFR；
- 一个可描述的用户结果和明确非目标；
- capability owner、依赖、fixture 与风险 ID；
- 正常、边界、失败和恢复验收场景。

缺少稳定需求或目标版本时，不进入契约设计。

### Gate S1：Contract Ready

必须具备：

- capability 拥有的业务接口与不变量；
- 该切片所需的 API 请求、响应、错误、认证、幂等和分页/Range 语义；
- schema/migration、唯一约束、事务边界和恢复语义；
- 威胁边界、资源上限、日志脱敏与可观察状态；
- 合成 fixture 和自动化测试计划。

当前公开 API 的结构必须先在 `api/openapi.yaml` 中修改并评审，API 设计说明不得覆盖 wire
契约。migration 是源文件且只追加。不得以 UI mock 或 handler 临时结构替代契约。

### Gate S2：Backend Evidence Ready

必须证明：

- 业务规则在 capability 层，HTTP handler 未直接访问 SQLite、真实路径或媒体工具；
- adapter 通过真实临时目录/真实文件 SQLite 等适当集成测试；
- 路径、事务、并发、取消、离线、重启和错误脱敏中的适用场景通过；
- 数据库事务期间不执行文件系统或媒体处理；后台任务有界、可取消、可重试；
- 适用的 OpenAPI lint/契约、migration、生成漂移和 `arch-check` 已实际执行并通过。检查不存在、
  无法执行或结果未知时，S2 只能是 `Conditional Go` 或 `No-Go`，不能记录为 `Go`。

阶段 0 spike 可以先于完整产品契约存在，但 spike 代码不得直接晋升为产品实现；晋升前必须重新通过 S0～S2。

### Gate S3：Consumer/UI Ready

必须具备：

- UI 只消费已评审契约和统一客户端，不创建平行数据语义；
- server state、URL state、分页和虚拟化符合前端约束；
- 加载、空、错误、离线、取消和权限状态中的适用项；
- 键盘、焦点、语义、语言和 reduced-motion 行为；
- 组件/交互测试，以及不会隐藏后端安全错误的文案映射。

### Gate S4：Integrated Slice Done

必须具备：

- 从 UI/HTTP 到 capability、SQLite/文件适配器的端到端证据；
- 对应容器、恢复、性能或媒体 fixture 门槛（适用时）；
- PRD、用户流程、API、数据、安全、部署和 README 的受影响内容已同步；
- [Definition of Done](../development-readiness.md#definition-of-done) 满足；
- 追踪表中的测试列由“计划”更新为实际证据链接。

只有 S4 完成，切片才可计入阶段出口。局部 package 测试通过不能替代切片完成。

## Gate 记录

阶段、版本和切片 Gate 都使用相同最小记录，并存放为：

```text
docs/gates/<target-version>/<stage-or-slice>-<gate>.md
```

实施 PR/Change Record 必须链接当前 Gate；普通修复可以复用所属切片 Gate，不为每个提交复制记录。
没有可审计记录不能仅凭口头或 PR 描述进入下一 Gate。

```markdown
# Gate <版本>/<阶段或切片>/<Gate>

- 日期：
- 目标版本：
- Roadmap 阶段：
- 需求：FR-/NFR-
- 决策角色：产品 / 架构 / capability / 安全或数据 / 发布
- 输入与证据：
- 未关闭风险与 fallback：
- 结论：Go | Conditional Go | No-Go
- Conditional 条件、Owner、复审触发：
- 下一步获准范围：
```

结论规则：

- `Go`：全部必需输入和证据满足，可进入记录的下一范围。
- `Conditional Go`：只允许不依赖缺失条件、且不扩大信任边界的工作；必须记录条件、Owner 和复审触发。
- `No-Go`：停止相关实施，选择缩减范围、替代方案或新 ADR，不能用更多代码绕过。
- Gate 结论必须链接证据；复述计划不算证据，口头同意不能关闭风险。
- 适用检查未执行或检查入口尚不存在时不得给出 `Go`；只能给出有范围限制的 `Conditional Go`
  或停止推进的 `No-Go`。

## 角色与决策职责

| 角色 | 决策职责 |
| --- | --- |
| 产品负责人 | 用户价值、MVP/未来归属、scope trade-off 和产品验收 |
| 架构负责人 | 影响分析、ADR、能力边界、质量属性和架构一致性 |
| Capability Owner | 切片设计、依赖、实施证据和运行责任 |
| 安全/数据负责人 | 信任边界、原件安全、迁移、恢复和发布阻断风险 |
| 发布负责人 | 版本清单、Gate 汇总、残余风险、构建与恢复证据 |

同一人可以承担多个角色，但 Gate 记录中必须分别写明职责。Agent、代码作者或实现完成本身不能代替产品范围确认或发布批准。

## 豁免与例外

豁免默认不批准。确需豁免时必须记录：适用版本和部署范围、原因、受影响 Gate、风险、缓解、fallback、Owner、复审触发和失效条件。

以下项目不可豁免：

- 写入或破坏原始媒体；
- 读取 `/library` 或媒体库根之外的内容；
- 失败、取消、离线或部分扫描清理旧索引；
- 未认证稳定版或匿名 LAN 模式；
- 修改已发布 migration 或伪造测试/发布证据；
- 带有未处置严重安全、数据完整性或许可证阻断项的稳定发布。

性能、平台或非核心体验的降级只有在产品和架构负责人共同记录影响、目标版本与复审条件后才可接受。豁免不得永久泛化到未来版本。

## 计划中的自动化约束

阶段 1 建立 CI 后，应逐步把以下规则变为 architecture fitness functions：

- 禁止的包依赖和未经 ADR 新增的部署单元/外部服务；
- OpenAPI 与生成代码漂移；
- migration 只追加及已发布文件不可变；
- 路径逃逸、generation 故障、SQLite WAL/完整性和原媒体无写入；
- 游标分页、虚拟化、目标容量预算和后台队列上限；
- 双架构容器、备份恢复、SBOM、漏洞和许可证门槛。

在这些检查尚未落地前，Gate 记录必须明确标为人工检查或未执行，不能声称已自动保障。
