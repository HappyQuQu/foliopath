# 已知问题：自动发现失败后的重复全量回退

2026-10-29 用户报告任务历史连续出现同库的完整扫描。本记录为只读调查，不包含修复或生产配置变更，不能将其列为本次发行已修复问题。

- 实例：222 / 正式v1.8.0，`test`库；扫描设置仍为24小时、自动发现开启。16:31前后记录显示完整扫描约每20～30秒新建一次，成功发现27,817个媒体、423个目录；并非同一任务一直未结束。
- 直接证据：SQLite记录中该库自动发现增量任务失败，固定错误为internal_error；最后一轮完整扫描在16:47:05～16:47:07以scan_io_error失败，调查时queued/running完整扫描数为0，自动发现降级。容器内database-check通过。未凭通用错误断言具体文件或压缩格式是根因。
- 代码路径：automaticDiscoveryCoordinator 的增量失败回退可经RequestAutomaticFallback创建trigger=scheduled完整扫描；degradeAndFallback以当前generation阻止重试，但成功全扫推进generation后reconfigure会重新准入监视。如果后续增量再次失败，仍可再次全扫；仅定时扫描间隔无法约束这条路径。历史“定时任务”也不能区分真正定时与自动发现回退。
- 限制：服务器日志未保留增量失败的底层异常，最初失败原因尚未确定；回退缺少跨成功generation的抑制这一问题已定位。文件变化是否由外部持续写入导致，不能从现有记录确定。
- 临时处理：若重复发生，在界面关闭自动发现后改用手动或定时完整扫描；仅关闭定时扫描不足以停止自动发现回退。此处理会延迟文件新增/删除的自动反映，手动/后续成功全扫继续负责核对。调查没有修改设置或删除任务/索引，没有重启或升级222。
- 后续修复须保留真实新增/删除的发现、失败扫描保留已有索引、可恢复的手动/定时扫描；在合成目录重现增量失败与回退循环并取得底层诊断后，再确定有界恢复合同与回归。本记录不授权改写现有任务历史或将未知错误归为坏媒体。
