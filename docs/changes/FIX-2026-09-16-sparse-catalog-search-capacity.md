# P4 稀疏文件名搜索容量修复

- 范围：CR-2026-030 / NFR-INT-002、NFR-INT-003 / POST-MVP-5 P4 E01。
- Owner：catalog / SQLite / QA。
- 状态：已实现，最终本地 Docker 基础容量与专项 race 通过；不关闭 P4 整体。
- 合同：现有文件名/路径包含匹配、库隔离、排序与认证游标均不变；无新索引、表、端点或缓存。

最终 P2/P3 镜像在本地 Linux/arm64、4 CPU / 4 GiB、100k 媒体/10k 目录中，库内文件名搜索 P95 815.744 ms、全库 436.703 ms，超过既有 250 ms。首次运行还发现容量脚本 `/tmp` 固定旧 UID 的测试配置错误，已单独修复。

候选改动将稀疏查询排序扫描中的相关 FTS `EXISTS(rowid=a.id AND MATCH)` 改为非相关 `a.id IN (SELECT rowid ... MATCH)`。避免稀疏命中位于排序末尾时对每个资产重复执行 MATCH；仍由 SQLite 构造候选集，并继续应用既有 instr 精确过滤、范围、排序和 keyset。不预先把整个目录读入 Go 内存。

第一轮候选的稀疏搜索达标，但新增宽查询仍为 397.505/373.158 ms，整轮失败。进一步由 catalog 把已经计算或从认证游标读取的 MatchCount 传给仓储，作为内部查询计划提示：命中 ≥10k 时省略 FTS 加速器，直接使用原排序索引与同一组 instr 精确谓词。提示不参与匹配和鉴权，不缓存新状态，不改变公开 DTO/游标格式；即使提示不准确也只能影响速度。新增 0/9999/10000/1000000 提示结果逐 ID 等价检查。

第二轮全局宽查询降至 175.036 ms，但库内宽查询仍为 422.417 ms，继续判失败。计数的库过滤使普通 JOIN 可以选择库索引为外层并反复探测 MATCH；第三轮用 SQLite CROSS JOIN 固定 FTS 驱动资产主键查找，精确谓词/统计分类不变。没有增加计数缓存或近似计数。

新增双库稀疏/广泛/零命中游标测试，验证每页统计、范围、排序、无重复与无遗漏；既有 Unicode、多词、过滤及库内/全局测试继续执行。性能必须重测稀疏与广泛查询；不能只凭 SQL 改写就称优化通过。

当前执行证据：[P4 质量与容量](../evidence/int-001/p4-quality-capacity-2026-09-16.md)。不关闭 AI 联合负载、真实模型质量或原生双架构。

最终 100k/10k、4 CPU/4 GiB 单应用：扫描 118 秒，稀疏库内/全局 P95 163.016/76.785 ms，宽查询 123.460/163.381 ms，全部低于原 250 ms；峰值内存 320,376,832 bytes。SQLite 专项、API、contract race 及格式/架构检查通过，详见执行记录的固定镜像摘要与保留失败记录。
