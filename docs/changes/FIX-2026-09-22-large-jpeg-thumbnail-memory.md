# FIX-2026-09-22：超大 JPEG 缩略图内存与崩溃恢复

状态：实现与派生媒体验证完成；全库 AI 长任务验证进行中。

范围：FR-MED-013、FR-SCN-006、NFR-OPS-003；POST-MVP-5 候选的派生媒体处理，
不改变原媒体、公开 API、持久化格式或双容器部署边界。

## 问题

在 1 GiB 主应用限制下，对 `coser` 测试库执行首次派生媒体处理时，两个 50–109 MiB、
约 1 亿像素的高质量 JPEG 同时进入 libvips，容器出现 OOM。连续崩溃还会留下多于
worker 数量的过期租约；旧恢复逻辑把这种可恢复积压视为全局错误，导致后续启动循环退出。

## 修复

- JPEG 在第一次原生加载前用标准库读取并校验尺寸；生产 Linux 通过 `/proc/self/fd/<fd>` 将
  已由 openat2 锚定的文件直接交给 libvips decoder-level shrink，避免 Go 保留 50–109 MiB
  源缓冲。缩略后再执行 EXIF 自动旋转，保留原始方向后的完整尺寸元数据。
- 源读取先获取并校验大小，只分配一次精确缓冲区；64 KiB 分块检查取消，并拒绝读取期间
  的缩短、增长和无进展读取。
- 主派生媒体 worker 从 2 收紧为 1。真实样本证明两个约 1 亿像素 JPEG 并发时会达到
  960–990 MiB，而单 worker 峰值仍可达到约 873 MiB；1 GiB 配额下必须串行化。
- 过期租约恢复改为每轮最多处理一个 worker-sized 批次，由周期恢复继续排空，不再因历史
  崩溃留下多条租约而终止整个应用。
- 生命周期日志只增加安全的组件名称，不输出 SQL、路径或底层错误文本，便于确认退出 owner。
- 远程语义预处理使用同一 FD 流式边界，JPEG 上限从旧 64 MiB 对齐到既有媒体合同 256 MiB，
  预处理身份升级为 v3；只对已通过格式/尺寸校验且命中既有窄 allowlist 的截断 JPEG重试一次。
- 简化设置页的智能搜索和人物分析开关在成功启用后自动提交 missing 任务并记录 operation；关闭
  仍只更新设置。
