# ADR-0006：采用契约驱动、切片内后端优先的交付顺序

## 状态

已接受（2026-07-23）

## 决策角色

- 产品：确认稳定 MVP 必须控制范围并优先形成可发布闭环
- 架构：系统架构与交付顺序评审
- 安全/数据：涉及路径、认证、迁移和扫描清理的切片不得由 UI mock 先定义语义

## 背景

FolioPath 同时包含 Go 后端、React 前端、SQLite、文件系统边界和原生媒体工具。若前端先依据
临时对象发明业务行为，或后端在没有 API／数据契约时并行铺开包，错误、状态、分页和恢复
语义会在多处形成事实标准，后续集成与安全修复都需要返工。

项目又不能采用“全部后端结束后才允许任何前端工作”的瀑布流程。应用壳、设计系统、可丢弃
原型和真实组件状态需要尽早验证，但它们不能替代后端契约。

## 备选方案

1. **前端先行并长期使用手写 mock。** 视觉反馈快，但字段、状态、错误和权限容易成为第二套契约。
2. **全后端完成后才开始任何前端。** 边界稳定，但形成大型瀑布，交互与可访问性风险暴露过晚。
3. **契约驱动的纵向切片，切片内后端优先。** 只稳定当前能力所需后端，同时允许最小、可丢弃的设计验证。

选择方案 3。

## 决策

- 采用**纵向切片内后端优先**，而不是全项目后端瀑布。每个用户能力按以下门禁推进：
  1. `S0 Architecture Ready`：切片、需求、质量属性、所有者、失败语义和架构影响已明确。
  2. `S1 Contract Ready`：OpenAPI、数据／迁移、错误码、鉴权和状态机已接受。
  3. `S2 Backend Ready`：领域服务、适配器、契约测试与跨组件集成测试通过。
  4. `S3 Frontend Ready`：前端使用生成客户端和共享设计系统实现全部适用状态。
  5. `S4 Integrated Slice Done`：当前切片的 E2E、适用容器/故障、文档与追踪证据通过。
- `Release Ready` 是版本级 Gate，不属于单个切片。只有全部版本内切片完成，且容量、安全、恢复、
  双架构、合规和发布文档门槛通过后，版本才可进入 Release Ready。
- 业务前端不得长期依赖与正式契约无关的 mock，不得直接猜测字段、错误、分页、重试或权限行为。
- 已通过 S0、进入 S1 的当前切片直接需要的最小 React/Vite 应用壳、路由骨架、token、共享原语、
  组件工作台和可丢弃交互原型可以按时间盒在 `Backend Ready` 前并行。原型不得进入生产 import
  graph、形成独立契约或被描述为已完成产品能力；不能为未来 feature 提前铺开设计系统。
- 首个受保护业务 API 之前必须建立管理员初始化、登录／会话校验、退出和 CSRF 的基础边界。
  发布阶段负责进一步完成限流、代理信任、恢复与安全演练，而不是最后才把认证横插进所有接口。
- 同一时间优先完成一条可运行、可故障注入的切片；切片未通过时不并行铺开搜索、分享、EXIF、
  watcher 或其他后续能力。
- 生成客户端是前后端结构化契约边界；手写前端 adapter 可以组合领域友好类型，但不得形成第二套
  HTTP client 或复制服务端业务校验。

## 后果

- API、错误、状态与权限在前端实现前已有可执行证据，减少双端漂移和返工。
- 后端测试先覆盖安全和故障语义，UI 可以专注于交互状态，而不是承担数据正确性。
- 设计系统和原型仍能较早验证，不会因为“后端优先”阻塞所有视觉工作。
- 每条切片需要显式门禁和契约维护，早期看起来比自由并行更慢，但能限制在制品与隐藏集成成本。

## 验证与复审

- 由 `make arch-check`、OpenAPI 生成漂移、后端契约／集成测试和 E2E 门禁逐步执行。
- 若真实交付数据证明该顺序持续阻塞独立工作，可复审门禁粒度；不得取消契约权威或安全边界。
